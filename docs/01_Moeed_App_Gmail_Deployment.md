## M1 | Foundation and OAuth, 00:00–01:15

1. Install Git and Python 3.11. In PowerShell run `git --version` and `py -3.11 --version`. Follow the shared guide for the first commit and branch. Create your virtual environment with `py -3.11 -m venv .venv`. Use `.\.venv\Scripts\python.exe` for pip, pytest and uvicorn to avoid shell activation issues. [Python for Windows](https://www.python.org/downloads/windows/)
2. Ask the assistant for a minimal FastAPI homepage, GET /health, a Dockerfile listening on the Cloud Run PORT, and tests/app/. Use plain HTML/CSS plus small JavaScript. The health check must start before OAuth or Gemini is configured. Keep credentials in local environment variables or an ignored .env read by your app; put only variable names and example nonsecret defaults in .env.example.
3. Use the project selector in Cloud Console. In APIs & Services → Library enable Gmail API, Cloud Run, Cloud Build, Artifact Registry, Firestore, Secret Manager and Cloud Scheduler as needed. In Firestore create one Native mode database and pick its location with your teammate. Prefer a nearby supported region for the app. Keep the web frontend talking to your backend; use a dedicated runtime service account with database access and access to only its required secrets. For local development use Application Default Credentials through `gcloud auth application-default login` with authorized project access. [Firestore setup](https://firebase.google.com/docs/firestore/quickstart)
4. Deploy the skeleton early. In Cloud Shell clone the repo and check out the branch/commit being deployed. Run the following there, replacing PROJECT_ID and REGION. The first deploy is only the health skeleton. Later attach secrets and runtime identity using Cloud Run → Edit and deploy new revision. Confirm the URL on the service details page. [Cloud Run source deployment](https://docs.cloud.google.com/run/docs/deploying-source-code)

```bash
gcloud config set project PROJECT_ID
gcloud run deploy subguard-web --source . --region REGION --allow-unauthenticated
```

5. In **Google Auth Platform → Branding**, enter app name, support email and developer contact. Under **Audience**, choose External/Testing for this demo and add your dedicated Gmail address to Test users. Under **Data Access** add exactly the Gmail scope `https://www.googleapis.com/auth/gmail.readonly`. Under **Clients**, create a Web application OAuth client. Register both complete redirect URIs: `http://localhost:8000/auth/google/callback` and `https://YOUR_DEPLOYED_HOST/auth/google/callback`. Put the client ID and secret in server configuration. Localhost and 127.0.0.1 count as different hosts. [Google Auth Platform](https://console.cloud.google.com/auth/overview) · [Testing audience](https://support.google.com/cloud/answer/15549945) · [Gmail scope descriptions](https://developers.google.com/workspace/gmail/api/auth/scopes)
6. Implement server-side authorization-code flow with the Google auth libraries. Store and verify a short-lived single-use state value bound to the browser session. Use a secure opaque HttpOnly session cookie in production. Exchange the callback code server-side; verify the granted permission; identify the connected mailbox with Gmail's authenticated profile. Keep an account-scoped identifier on the server. Use online access for connect/refresh in this demo. Store short-lived tokens server-side, encrypt persisted tokens, expire them and offer Reconnect. Exclude tokens and raw mail from request logs. [Web OAuth flow](https://developers.google.com/identity/protocols/oauth2/web-server)
7. Show one line before consent explaining the billing-email search and the records kept. On successful callback automatically run the first scan. If consent is denied return to a usable Connect screen. **Gate:** On the hosted site, connect the team mailbox, find one known receipt, inspect the source and refresh the page successfully. If the callback fails compare the exact registered URI, project, client type and tester address.

## M2 | Gmail to billing events, 01:15–02:15

1. Search approximately the previous 13 months using Gmail messages.list with a q filter covering receipt, invoice, renewal, trial, subscription, auto-renew, payment and cancellation words. Example starting query: `newer_than:13m {receipt invoice renewal trial subscription payment cancellation "auto-renew"}`. Follow nextPageToken, fetch candidates via messages.get, and display a cap/partial flag when a page or request limit is reached. Interpret the result as “subscriptions found in searched email.” [Gmail filtering](https://developers.google.com/workspace/gmail/api/guides/filtering) · [List and get messages](https://developers.google.com/workspace/gmail/api/guides/list-messages)
2. Decode base64url data, walk multipart parts, prefer plain text, strip markup from an HTML fallback and skip attachments in this build. Use opaque source IDs, map them to the correct Gmail account/message and expose a verified source link only within its owner's session. Test the link in the demo browser, including when multiple Google accounts are signed in. Redact quoted text and personal identifiers before handing the §2 envelope to Ahmed. Use a dedicated synthetic mailbox with the team's approved model setup for the demonstration.
3. Call extract_events; validate and upsert by account and event ID. Reload all known events for this account and call build_portfolio. Preserve history if Gmail times out or returns partial results. Keep per-account scan versions so an old, slow refresh cannot overwrite a newer completed scan. On repeated refresh, rereading the same source yields the same event ID.
4. Keep account-owned collections for evidence, events, latest portfolio, review items, reminder jobs and notifications. Keep source IDs on events and review items. Persist only necessary fields. For reviewer examples use a new isolated session and synthetic records. **Gate:** duplicate email yields two evidence links and one payment. An empty mailbox, a failed scan and a successful zero-result scan get distinguishable states.

## M3 | Dashboard and agent integration, 02:15–04:15

1. Render three figures **per currency**: paid during the scan window, forward monthly equivalent, and confirmed charges due this week. Label annual renewals with their full due amount and date. Provide a subscription list, dates marked Confirmed/Estimated/Unknown, evidence links, last successful scan and a Refresh button. Show partial scans. Keep trial conversions separate from already paid plans.
2. On connect/refresh, await run_review from Ahmed's package. Persist only proposals whose subscription and evidence belong to the active snapshot and account. Commit each update against the active scan revision, upsert stable keys and resolve superseded items. Show the real tool names/results. When a tool fails, retain the last good result and show a retry state. A mock adapter may power tests; the hosted live screen must never silently fall back to it.
3. A click on **Remind me** authorizes one in-app job for a confirmed date. Revalidate account, target and current renewal state. Persist due_at in UTC, display Asia/Karachi, and use a stable job/notification ID. Choose a documented demo default such as the previous day at 09:00 local; if already past, offer an immediate review instead. Provide a separate labeled one-minute test option. Browser requests need session validation and CSRF protection. Scope deduplication to the account, target and reminder type.
4. Deploy a second Cloud Run service from the same source with worker-only entry point or `SERVICE_MODE=worker`, authentication required. Configure the web service so it never mounts the delivery route. In Cloud Scheduler create an HTTP POST job every minute (`* * * * *`) to the private worker's /jobs/deliver. Select **OIDC**, use a dedicated calling service account with Cloud Run Invoker on that worker, and set the audience to the worker's base service URL. Give the worker's own runtime identity access to only the database resources it needs. A Firestore transaction rechecks due time and latest evidence, writes one notification and marks the job delivered together. A cancellation invalidates outstanding jobs for that charge. [Scheduler HTTP authentication](https://docs.cloud.google.com/scheduler/docs/http-target-auth) · [Firestore transactions](https://firebase.google.com/docs/firestore/manage-data/transactions)
5. **Gate:** fixture totals match §3 of the shared guide, the trace shows a real MCP call, and a reminder delivered while the tab was closed appears once after two worker attempts.
